# **AGENTS.md**

## **Scope**

These instructions apply to the entire repository unless a nested `AGENTS.md` overrides them for a specific directory.

This repository is a Spring Boot backend application.

The agent must preserve the existing architecture, conventions, public contracts, and behavior unless the task explicitly requires changing them.

## **Core Rules**

1. Inspect before modifying.  
2. Make the smallest change that fully solves the task.  
3. Follow existing project conventions over generic best practices.  
4. Do not redesign unrelated code.  
5. Do not introduce dependencies unless necessary.  
6. Do not change public API contracts unless explicitly requested.  
7. Do not modify database schema casually.  
8. Do not suppress failures instead of fixing their cause.  
9. Never claim a change works without validating it.  
10. Keep the repository buildable.

## **Before Making Changes**

Before editing code, inspect the relevant parts of the repository.

At minimum, check:

* `pom.xml` or `build.gradle`  
* `src/main/java`  
* `src/main/resources`  
* `src/test/java`

For the affected feature, identify:

* Controller  
* Service  
* Repository  
* Entity  
* DTOs  
* Mapper  
* Exceptions  
* Tests  
* Configuration

Search for existing implementations of similar behavior before creating new abstractions.

Prefer reuse over duplication.

Do not assume:

* Java version  
* Spring Boot version  
* database engine  
* Lombok availability  
* MapStruct availability  
* Spring Security configuration  
* testing libraries  
* naming conventions  
* package structure

Determine them from the repository.

## **Build System**

Use the build system already present in the project.

For Maven:

./mvnw test

On Windows:

mvnw.cmd test

If no wrapper exists:

mvn test

For Gradle:

./gradlew test

Do not migrate Maven to Gradle or Gradle to Maven unless explicitly requested.

## **Architecture**

Preserve the existing application architecture.

Typical Spring Boot flow:

Controller  
    ↓  
Service  
    ↓  
Repository  
    ↓  
Database

If DTOs and mappers exist:

HTTP  
 ↓  
Request DTO  
 ↓  
Controller  
 ↓  
Service  
 ↓  
Repository  
 ↓  
Entity  
 ↓  
Response DTO

Do not bypass layers without a good reason.

Examples of prohibited shortcuts:

Controller → Repository  
Controller → EntityManager  
Controller → database query  
DTO → Repository  
Entity → Service

unless the existing architecture intentionally uses that pattern.

## **Controllers**

Controllers handle HTTP concerns.

Controllers may:

* receive parameters  
* receive request bodies  
* validate request DTOs  
* call services  
* return response DTOs  
* select HTTP status codes

Controllers should not contain business logic.

Prefer constructor injection.

@RestController  
@RequestMapping("/api/locals")  
public class LocalController {

    private final LocalService localService;

    public LocalController(LocalService localService) {  
        this.localService \= localService;  
    }  
}

Do not introduce field injection.

Avoid:

@Autowired  
private LocalService localService;

unless the existing project consistently uses field injection and changing it is outside task scope.

## **Services**

Business logic belongs in services.

Services are responsible for:

* business rules  
* orchestration  
* persistence coordination  
* transactional operations  
* state transitions  
* domain validation  
* resource existence checks

Prefer constructor injection.

Keep service methods cohesive.

Do not create large service methods when existing logic can be decomposed clearly.

Do not split simple logic into unnecessary abstractions.

## **Repositories**

Repositories handle persistence.

Prefer existing Spring Data repository patterns.

public interface LocalRepository extends JpaRepository\<Local, Long\> {  
}

For simple queries, prefer derived query methods:

Optional\<User\> findByEmail(String email);

boolean existsByCode(String code);

Use JPQL or native SQL only when necessary.

Before creating a custom query, check whether:

* a derived query already exists  
* an equivalent repository method exists  
* JPA can express the operation cleanly

Never add business logic to repositories.

## **Entities**

Treat entities as persistence models.

When modifying entities:

* preserve table mappings  
* preserve relationship ownership  
* consider fetch strategy  
* consider cascade behavior  
* consider nullability  
* consider database constraints  
* consider serialization recursion  
* consider equality semantics

Do not change mappings such as:

@Entity  
@Table  
@Column  
@JoinColumn  
@OneToMany  
@ManyToOne  
@OneToOne  
@ManyToMany

without understanding the database impact.

Never casually change relationship cascade settings.

Especially avoid introducing:

CascadeType.ALL

without a clear reason.

## **DTOs**

If DTOs exist, preserve the entity/API boundary.

Do not expose JPA entities directly through controllers if the project already uses DTOs.

Follow existing DTO naming conventions.

Examples:

CreateUserRequest  
UpdateUserRequest  
UserResponse

or:

UserDTO

Do not introduce a new DTO naming scheme into an established project.

## **Mapping**

Use the mapping strategy already present.

If the project uses:

* MapStruct  
* manual mapper classes  
* static factory methods  
* service-level mapping

continue using that approach.

Do not add MapStruct merely to eliminate small manual mappings.

Do not add Lombok merely to reduce boilerplate.

## **Dependency Injection**

Prefer constructor injection.

private final UserRepository userRepository;

public UserService(UserRepository userRepository) {  
    this.userRepository \= userRepository;  
}

If Lombok is already used consistently:

@RequiredArgsConstructor  
@Service  
public class UserService {

    private final UserRepository userRepository;  
}

is acceptable.

Never introduce Lombok without checking `pom.xml` or `build.gradle`.

## **Validation**

Use Jakarta Bean Validation when appropriate.

Typical annotations:

@NotNull  
@NotBlank  
@Size  
@Email  
@Min  
@Max  
@Positive  
@Pattern

Controller request bodies should use:

@Valid

when validation annotations are present.

Validation involving persisted state belongs in the service layer.

if (userRepository.existsByEmail(request.email())) {  
    throw new DuplicateResourceException(...);  
}

Do not duplicate validation across controller and service without reason.

## **Exceptions**

Use the project's existing exception strategy.

Before adding a new exception, inspect:

* `@RestControllerAdvice`  
* `@ControllerAdvice`  
* `@ExceptionHandler`  
* custom `RuntimeException` classes  
* error response DTOs

Prefer centralized exception handling.

Do not catch exceptions only to hide them.

Avoid:

try {  
    ...  
} catch (Exception e) {  
    return null;  
}

Avoid:

catch (Exception e) {  
    e.printStackTrace();  
}

Do not convert all exceptions into `500` manually if centralized handling exists.

## **Resource Lookup**

For required resources, prefer:

repository.findById(id)  
        .orElseThrow(() \-\> new ResourceNotFoundException(...));

Avoid:

repository.findById(id).get();

Do not return `null` for missing resources unless the existing contract explicitly requires it.

## **Transactions**

Use transactions at the service layer.

For write operations requiring atomicity:

@Transactional

For complex reads where appropriate:

@Transactional(readOnly \= true)

Do not add `@Transactional` indiscriminately.

Understand whether JPA dirty checking is being relied upon.

When modifying a managed entity inside a transaction, an explicit:

repository.save(entity);

may not be necessary.

Follow the current project's persistence style unless there is a concrete reason to change it.

## **Update Semantics**

Respect the intended distinction between `PUT` and `PATCH`.

For partial updates, validate each field independently.

Wrong:

if (request.getCode() \!= null) {  
    entity.setFloor(request.getFloor());  
}

Correct:

if (request.getFloor() \!= null) {  
    entity.setFloor(request.getFloor());  
}

When updating Strings, distinguish between:

* `null`  
* empty string  
* blank string  
* actual value

according to the API contract.

Do not silently invent update semantics.

## **REST Conventions**

Preserve existing routes.

For new REST resources, prefer conventional resource-based routes:

GET    /api/users  
GET    /api/users/{id}  
POST   /api/users  
PUT    /api/users/{id}  
PATCH  /api/users/{id}  
DELETE /api/users/{id}

Use appropriate HTTP statuses.

Typical defaults:

GET     → 200  
POST    → 201  
PUT     → 200 or 204  
PATCH   → 200 or 204  
DELETE  → 204

Errors commonly map to:

400 Bad Request  
401 Unauthorized  
403 Forbidden  
404 Not Found  
409 Conflict  
500 Internal Server Error

Do not change existing API semantics merely to make them more theoretically RESTful unless requested.

Backward compatibility has priority.

## **Spring Security**

If Spring Security exists, inspect the current security configuration before modifying endpoints.

Check for:

* `SecurityFilterChain`  
* `@EnableMethodSecurity`  
* `@PreAuthorize`  
* `@Secured`  
* filters  
* JWT handling  
* authentication providers  
* CORS configuration  
* CSRF configuration

Do not disable security to make tests pass.

Never solve authorization problems with:

.anyRequest().permitAll()

unless explicitly requested.

Do not expose previously protected endpoints accidentally.

## **Persistence**

Before changing persistence behavior, determine:

* database engine  
* migration system  
* schema generation mode  
* entity relationships  
* current constraints

Check configuration such as:

spring.jpa.hibernate.ddl-auto  
spring.datasource.\*

and migration folders such as:

db/migration  
liquibase  
flyway

## **Database Migrations**

If Flyway or Liquibase is used, schema changes must follow the existing migration mechanism.

Never modify an already-applied migration unless the repository explicitly treats migrations as disposable.

Prefer creating a new migration.

Example:

V1\_\_initial\_schema.sql  
V2\_\_add\_user\_status.sql  
V3\_\_add\_local\_code\_index.sql

Database changes must be backward-aware when possible.

## **Configuration**

Do not hardcode environment-specific values.

Avoid:

String password \= "password123";  
String url \= "http\://localhost:8080";

Use Spring configuration:

* `application.properties`  
* `application.yml`  
* environment variables  
* `@ConfigurationProperties`  
* `@Value`

Follow existing configuration patterns.

Never commit:

* passwords  
* API keys  
* private keys  
* access tokens  
* database credentials  
* JWT secrets

## **application.properties / application.yml**

Preserve profile separation.

Possible profiles:

application.yml  
application-dev.yml  
application-test.yml  
application-prod.yml

Do not move production configuration into default configuration casually.

Do not enable destructive schema generation in production.

Be especially careful with:

spring.jpa.hibernate.ddl-auto=create  
spring.jpa.hibernate.ddl-auto=create-drop

## **Logging**

Use the project's logging framework.

For Spring Boot this is normally SLF4J.

Prefer:

private static final Logger log \=  
        LoggerFactory.getLogger(MyService.class);

or Lombok `@Slf4j` if already used.

Do not use:

System.out.println(...)  
System.err.println(...)

for application logging.

Do not log:

* passwords  
* access tokens  
* authorization headers  
* private keys  
* sensitive personal data

## **Code Style**

Match existing source style.

Preserve:

* indentation  
* brace style  
* naming  
* package organization  
* import ordering  
* annotations style  
* record/class usage  
* null-handling conventions

Do not reformat entire files unless necessary.

Avoid unrelated whitespace changes.

Avoid wildcard imports:

import java.util.\*;

unless the existing formatter enforces them.

## **Naming**

Use conventional Java names:

ClassName  
InterfaceName  
methodName  
variableName  
CONSTANT\_NAME  
package.name

Use domain terminology already present in the repository.

Do not rename domain concepts simply because another term seems cleaner.

## **Null Handling**

Prefer clear conditions.

Good:

value \!= null

Good for text:

value \!= null && \!value.isBlank()

Avoid unnecessary:

Objects.nonNull(value)

when a regular null check is clearer.

Never compare Strings using:

\==

Use:

equals()

or:

Objects.equals()

when null-safe equality is needed.

## **Collections and Streams**

Use streams when they improve clarity.

Do not replace simple loops with complicated stream pipelines merely for style.

Avoid side effects inside streams.

Bad:

users.stream()  
        .map(user \-\> {  
            user.setActive(true);  
            repository.save(user);  
            return user;  
        })  
        .toList();

Use explicit iteration for stateful operations when clearer.

## **Optional**

Use `Optional` primarily for return values representing optional results.

Avoid:

Optional\<User\> user \= Optional.ofNullable(...);

inside ordinary business logic unless useful.

Never use:

optional.get();

without guaranteed presence.

Prefer:

orElseThrow(...)

when the resource is required.

## **Tests**

Changes to behavior should normally include or update tests.

Use the testing strategy already present.

Potential test types include:

* unit tests  
* repository tests  
* `@WebMvcTest`  
* `@DataJpaTest`  
* `@SpringBootTest`  
* integration tests  
* Testcontainers

Do not turn every test into `@SpringBootTest`.

Prefer the smallest appropriate test scope.

## **Unit Tests**

Service tests should generally isolate dependencies using Mockito when the project follows unit-testing conventions.

Verify:

* successful behavior  
* missing resources  
* invalid states  
* boundary conditions  
* duplicate/conflict cases  
* update behavior

Do not test implementation details unnecessarily.

Test observable behavior.

## **Controller Tests**

When controller tests exist, verify:

* HTTP status  
* response body  
* validation  
* serialization  
* deserialization  
* error responses  
* service interaction

Use the project's existing MockMvc or WebTestClient approach.

Do not introduce a second HTTP testing framework unnecessarily.

## **Repository Tests**

Repository tests should focus on persistence behavior.

Typical annotation:

@DataJpaTest

Test custom queries and meaningful persistence behavior.

Do not write repository tests merely to prove that `JpaRepository.save()` works.

## **Test Data**

Tests must be deterministic.

Do not depend on:

* execution order  
* production data  
* local machine state  
* current date/time without control  
* random values without fixed seeds  
* external APIs unless explicitly integration-tested

## **External Services**

For integrations with external APIs:

* inspect existing client abstraction  
* preserve timeout behavior  
* preserve retry behavior  
* avoid real network calls in unit tests  
* mock at the appropriate boundary

Do not add retries blindly.

Retries can duplicate non-idempotent operations.

## **Date and Time**

Use `java.time`.

Prefer:

Instant  
LocalDate  
LocalDateTime  
OffsetDateTime  
ZonedDateTime  
Duration

Avoid introducing:

java.util.Date  
java.util.Calendar

unless required by existing APIs.

Be explicit about timezone when timestamps cross system boundaries.

## **Concurrency**

Do not introduce parallel execution without verifying thread safety.

Be especially cautious with:

parallelStream()  
@Async  
CompletableFuture  
custom Executor  
scheduled jobs

Consider:

* transactional context  
* request context  
* mutable state  
* entity manager boundaries  
* exception propagation

## **Performance**

Do not prematurely optimize.

However, watch for obvious persistence problems:

* N+1 queries  
* loading entire tables  
* unbounded result sets  
* repeated queries inside loops  
* eager relationship explosions

Use pagination for potentially large collections where the API architecture supports it.

Do not add caching without a demonstrated reason.

## **Security**

Treat all external input as untrusted.

Never construct SQL from raw user input.

Avoid exposing:

* stack traces  
* internal exception classes  
* filesystem paths  
* database details  
* secrets

through API responses.

Validate uploads, filenames, URLs, and identifiers when relevant.

Do not weaken security controls merely to simplify implementation.

## **Dependency Changes**

Before adding a dependency:

1. verify the required capability is not already available  
2. check for an existing library performing the same function  
3. ensure compatibility with the project's Java and Spring Boot versions  
4. prefer Spring-managed dependencies where possible

Do not upgrade unrelated dependencies.

Do not update the Spring Boot version unless the task requires it.

## **Refactoring**

Refactoring is permitted only when it directly supports the requested task or eliminates a clear defect encountered while implementing it.

Avoid unrelated cleanup.

Do not rename large portions of the codebase.

Do not perform architectural migrations without explicit instruction.

A bug fix should not become a repository-wide rewrite.

## **Compatibility**

Preserve compatibility unless explicitly instructed otherwise.

Consider:

* API contracts  
* JSON field names  
* database columns  
* URLs  
* HTTP statuses  
* configuration keys  
* environment variables  
* public Java APIs  
* tests  
* serialized values  
* enum names

Never casually rename serialized fields.

For example, changing:

private String userName;

to:

private String username;

may alter JSON and persistence behavior.

Check before changing.

## **Generated Files**

Do not manually edit generated files unless the project explicitly expects it.

Examples:

* `target/`  
* `build/`  
* `generated-sources/`  
* OpenAPI-generated code  
* compiled output  
* coverage output

Modify the source or generator configuration instead.

## **Files That Usually Must Not Be Modified**

Unless required by the task, avoid modifying:

* `.git/`  
* `.idea/`  
* `.vscode/`  
* `target/`  
* `build/`  
* `node_modules/`  
* `generated/`  
* binary files  
* lock files unrelated to dependency changes

Do not commit IDE-local state.

## **Git Discipline**

Keep changes focused.

Before completing the task, inspect:

git diff

and:

git status

Check for:

* unrelated modifications  
* accidental formatting  
* debug code  
* generated files  
* secrets  
* temporary files

Do not discard existing user changes.

Do not use destructive commands such as:

git reset \--hard  
git clean \-fd  
git checkout .

unless explicitly authorized.

Never overwrite unrelated uncommitted work.

## **Validation Procedure**

After implementing changes, perform the strongest validation reasonably available.

Preferred order:

1. Compile  
2. Run affected tests  
3. Run full test suite  
4. Run static checks or formatter if configured  
5. Inspect final diff

For Maven:

./mvnw test

If needed:

./mvnw clean verify

For Gradle:

./gradlew test

or:

./gradlew build

Do not report success if tests fail.

If tests cannot be run, state why.

## **Failure Handling**

If a build or test fails:

1. read the actual error  
2. identify whether it was introduced by the current change  
3. fix the root cause  
4. rerun the relevant validation

Do not:

* delete failing tests  
* disable tests  
* comment out assertions  
* catch exceptions broadly  
* remove validation  
* weaken security

just to make the build green.

Existing unrelated failures should be reported separately.

## **Implementation Strategy**

For non-trivial tasks:

1. inspect relevant code  
2. identify the current execution path  
3. identify affected contracts  
4. make the minimum coherent change  
5. update tests  
6. run validation  
7. inspect the diff

Do not begin by creating new abstractions.

First understand what already exists.

## **Decision Priority**

When instructions conflict, use this priority:

1\. Explicit user request  
2\. More specific nested AGENTS.md  
3\. Repository architecture and conventions  
4\. This AGENTS.md  
5\. General Spring / Java conventions

Do not override explicit project behavior with generic best practices.

## **When Requirements Are Ambiguous**

Infer intent from:

* existing implementation  
* tests  
* API conventions  
* domain naming  
* similar features  
* README / documentation  
* repository architecture

Prefer consistency with the repository.

Do not invent large requirements.

If multiple implementations are possible, choose the smallest solution compatible with existing patterns.

## **Definition of Done**

A task is complete only when:

* the requested behavior is implemented  
* existing architecture is respected  
* relevant tests are added or updated  
* affected tests pass  
* the project compiles  
* no obvious regression was introduced  
* no unrelated files were modified  
* no debug code remains  
* no secrets were added  
* the final diff has been reviewed

## **Final Response**

When reporting completed work, summarize:

* what changed  
* important implementation decisions  
* tests or validation performed  
* unresolved issues or limitations

Do not provide a long tutorial unless requested.

Do not claim that something was tested if it was not.

Do not claim that the application works merely because the code appears correct.

## **Primary Directive**

Understand the repository first.

Then make the smallest correct change that preserves its architecture and contracts.

Do not treat the repository as a blank project.

Do not optimize for generating more code.

Optimize for producing a correct, minimal, verified change.

# Functional Change Log

This specification defines how the **Documenter** generates project change reports.

The goal is not to produce an exhaustive line-by-line changelog. The goal is to preserve a readable history of **functional, structural, configuration, or behavioral changes** derived from real repository changes.

## Location and granularity

- Reports are stored under `docs/development-logs/`.
- **Each 30-minute interval may produce at most one Markdown file.**
- An interval with no relevant changes produces **no file**.
- Files are grouped by date.
- Recommended layout:

```text
docs/
└── development-logs/
    └── YYYY-MM-DD/
        ├── HH-mm--HH-mm.md
        ├── HH-mm--HH-mm.md
        └── ...
```

Example:

```text
docs/development-logs/2026-10-15/10-00--10-30.md
```

The filename represents **the interval being documented**, even if Gemini finishes writing later because it runs asynchronously.

## Source of truth: interval diff

The report must be generated from a **diff between the initial and final state of the interval**, not from any model's conversational memory and not from `git diff HEAD` as the sole source.

`git diff HEAD` answers: “What changed relative to the last commit?”

This log needs to answer: “What changed between the beginning and the end of these 30 minutes?”

### Monitor process

1. At the beginning of the interval, the external monitor captures a **working-tree snapshot S0**.
2. Development continues normally for 30 minutes.
3. At the end of the interval, the monitor captures **snapshot S1**.
4. The monitor generates the `S0 → S1` diff.
5. The diff must include:
   - modified files;
   - added files;
   - deleted files;
   - detectable renames;
   - staged and unstaged changes that are part of the observed state;
   - relevant new untracked files within project scope.
6. The monitor filters excluded paths and generated noise.
7. If no relevant change remains, it does not invoke the Documenter and creates no report.
8. If relevant changes exist, it gives Gemini the interval diff and the minimum required context.
9. Gemini writes **one report** for that interval at the expected path.

### Non-destructive capture

S0 and S1 must be obtained **without altering the user's real working tree or Git index**.

The capture mechanism must not use:

- automatic commits;
- `git stash push` on the real work;
- `git reset`;
- `git checkout`;
- operations that change the real index or discard user changes.

The recommended implementation uses temporary Git indexes, or an equivalent mechanism, to build temporary trees. Relevant untracked files must be included without modifying the user's real index.

The monitor may use auxiliary Git commands internally, but its contract is:

```text
S0 + S1 → immutable interval diff
```

The Documenter does not need to know how the snapshots were created. It only needs the resulting diff and, when available, additional metadata.

## Mandatory exclusions

The logging system's own output must never become input to the next interval.

Exclude at least:

```text
docs/development-logs/**
target/**
build/**
coverage/**
generated/**
node_modules/**
.idea/**
.vscode/**
.git/**
```

Add other generated project paths when appropriate.

This prevents loops such as:

```text
Gemini creates a log
→ the log appears in the next interval diff
→ Gemini documents that it created a log
→ another log-related change appears
```

## Recording criteria

- Group changes into **30-minute intervals**.
- Record only intervals with relevant changes.
- Create **at most one file per interval**.
- Include as many functional actions as necessary inside that file.
- Compare the initial and final state of the interval and omit intermediate edits that do not survive into the final state.
- Identify the affected element: function, component, entity, class, service, controller, repository, DTO, mapper, test, configuration, or other relevant element.
- Explain changes in behavior, responsibility, structure, contract, persistence, security, or configuration.
- Avoid mechanical details such as reordered imports, trivial setters, local-variable renames, formatting, or removed lines when they have no functional effect.
- Group several low-level edits when they form one functional action.
- Do not invent motives, effects, test results, or design decisions.
- When a fact cannot be determined from the diff or available context, state that explicitly.
- Do not include passwords, tokens, JWT secrets, API keys, credentials, authorization headers, or other secrets.
- Do not copy large code blocks unless required to explain a change.

## Context supplied to Gemini

Gemini should use **progressive disclosure** and consume the minimum context required.

Recommended initial input:

```text
1. S0 → S1 interval diff
2. git status --short or equivalent final-state metadata
3. affected-file list
4. available test result, if any
5. related spec/task, only if it can be identified reliably
```

Gemini must not read the whole repository by default.

If the diff is insufficient, it may open only:

- affected files;
- directly related interfaces or contracts;
- the related feature/task documentation;
- directly related tests.

Stop expanding context as soon as enough evidence exists.

## Asynchronous execution

The **Documenter** runs as an OpenCode v2 child/subagent in the background.

This means:

- the main development session can continue while Gemini writes the report;
- Gemini keeps its own model, context, and permissions;
- changing the main-session model does not change the model fixed for the Documenter;
- the generated filename always represents the documented interval, not Gemini's completion time.

OpenCode is not the clock. The 30-minute interval is controlled by an **external monitor**, such as a PowerShell process, which prepares the diff and decides whether the Documenter should be invoked.

## Idempotency and concurrency

The monitor must prevent one interval from accidentally producing two reports.

Rules:

- only one automatic execution may be launched for a given interval;
- if the interval file already exists, do not automatically create a second one;
- manual regeneration must be explicit;
- if Gemini finishes after the next interval has started, it must still write only the file for the interval it received;
- the next interval must use its own independent S0 and S1.

## Large diffs

If an interval diff is too large for convenient single-pass analysis:

- split analysis internally by file or area;
- keep the same interval;
- produce **one final report**;
- prioritize files with functional changes;
- open additional context only when necessary;
- do not split one interval into several log files unless a human explicitly decides to do so.

## Interval report template

```markdown
# Functional changes · [YYYY-MM-DD] · [HH:mm–HH:mm]

## Summary
[2–5 lines summarizing what changed during the interval.]

## 1. [Short description of the change]

**Element:** [Name and type of the affected element]  
**Files:** [Related file paths]  
**Action:** [Creation / Modification / Deletion]

**Before:**  
[What it did, what responsibility it had, or how it was configured at the beginning of the interval. If new, state that it did not exist or explain how the need was handled before.]

**After:**  
[What it does at the end of the interval.]

**Impact:**  
[What changes for users, other components, contracts, or execution. If external behavior is preserved, explain the relevant internal change.]

**Verification:**  
[Observed tests, compilation, or other checks. If there is no evidence: `Not verified`.]

[Repeat this block for every relevant functional action in the interval.]

## Relevant files

- `[path]` — [why the file matters]

## Global verification

[Summary of available test/build/check evidence, or `Not verified`.]
```

## What must not appear in a report

Omit noise unless it has a real functional effect:

- reordered imports;
- automatic formatting;
- local-variable renames;
- trivial setters/getters;
- intermediate edits later reverted;
- changes under `docs/development-logs/**`;
- compiled or generated files;
- secrets;
- claims about tests that were not executed.

## Final principle

The log describes **the observable change between S0 and S1**.

It does not describe the agent conversation, does not reconstruct every intermediate edit, and does not replace Git, tests, project requirements, or normal project documentation.

11. Crear el monitor externo de 30 minutos

Ubicación: tools/opencode/dev-log-monitor.ps1.

No toca tu índice real. Cada snapshot utiliza GIT_INDEX_FILE con un índice temporal, construye un tree Git y elimina ese índice temporal después.
dev-log-monitor.ps1 
param(
    [int]$IntervalMinutes = 30
)

$ErrorActionPreference = "Stop"

$RepoRoot = (git rev-parse --show-toplevel).Trim()
if (-not $RepoRoot) {
    throw "This script must run inside a Git repository."
}

Set-Location $RepoRoot

$StateRoot = Join-Path $env:TEMP "opencode-devlog-monitor"
New-Item -ItemType Directory -Force $StateRoot | Out-Null

$ExcludedPathspecs = @(
    ":(exclude)docs/development-logs/**",
    ":(exclude)target/**",
    ":(exclude)build/**",
    ":(exclude)coverage/**",
    ":(exclude)generated/**",
    ":(exclude)node_modules/**",
    ":(exclude).idea/**",
    ":(exclude).vscode/**",
    ":(exclude).git/**"
)

function New-WorkingTreeSnapshot {
    $tempIndex = Join-Path $StateRoot ("index-" + [guid]::NewGuid().ToString("N"))

    try {
        $env:GIT_INDEX_FILE = $tempIndex

        # Start from HEAD in a temporary index. The real Git index is untouched.
        git read-tree HEAD | Out-Null

        # Add the current working-tree state, including relevant untracked files.
        $pathspecs = @(".") + $ExcludedPathspecs
        & git add -A -- @pathspecs | Out-Null

        # Store the temporary tree and return its object ID.
        $tree = (& git write-tree).Trim()

        if (-not $tree) {
            throw "Could not create temporary Git tree."
        }

        return $tree
    }
    finally {
        Remove-Item Env:GIT_INDEX_FILE -ErrorAction SilentlyContinue
        Remove-Item $tempIndex -Force -ErrorAction SilentlyContinue
    }
}

function Get-IntervalArtifacts {
    param(
        [string]$StartTree,
        [string]$EndTree,
        [datetime]$StartTime,
        [datetime]$EndTime
    )

    $intervalId = "{0:yyyy-MM-dd}_{0:HH-mm}--{1:HH-mm}" -f $StartTime, $EndTime
    $artifactDir = Join-Path $StateRoot $intervalId
    New-Item -ItemType Directory -Force $artifactDir | Out-Null

    $diffFile = Join-Path $artifactDir "interval.diff"
    $metaFile = Join-Path $artifactDir "metadata.txt"

    $pathspecs = @(".") + $ExcludedPathspecs

    & git diff --binary --full-index --find-renames $StartTree $EndTree -- @pathspecs |
        Set-Content -Path $diffFile -Encoding UTF8

    $nameStatus = & git diff --name-status -M $StartTree $EndTree -- @pathspecs
    $finalStatus = & git status --short -- @pathspecs

    @(
        "Interval start: $($StartTime.ToString("yyyy-MM-dd HH:mm:ss"))"
        "Interval end:   $($EndTime.ToString("yyyy-MM-dd HH:mm:ss"))"
        "Start tree:     $StartTree"
        "End tree:       $EndTree"
        ""
        "Affected files:"
        $nameStatus
        ""
        "Final repository status:"
        $finalStatus
    ) | Set-Content -Path $metaFile -Encoding UTF8

    return @{
        DiffFile = $diffFile
        MetaFile = $metaFile
    }
}

function Start-Documenter {
    param(
        [datetime]$StartTime,
        [datetime]$EndTime,
        [string]$DiffFile,
        [string]$MetaFile
    )

    $dateDir = $StartTime.ToString("yyyy-MM-dd")
    $fileName = "{0:HH-mm}--{1:HH-mm}.md" -f $StartTime, $EndTime
    $targetRelative = "docs/development-logs/$dateDir/$fileName"
    $targetAbsolute = Join-Path $RepoRoot $targetRelative

    # Idempotency: never launch a second automatic report for the same interval.
    if (Test-Path $targetAbsolute) {
        Write-Host "Log already exists: $targetRelative"
        return
    }

    $promptArg = "Target output path: $targetRelative"

    # Launch OpenCode separately so development can continue immediately.
    # The command itself is configured to run the Documenter as a child/subagent.
    Start-Process `
        -FilePath "opencode" `
        -WorkingDirectory $RepoRoot `
        -ArgumentList @(
            "run",
            "--command", "document-interval",
            "--file", $DiffFile,
            "--file", $MetaFile,
            $promptArg
        ) `
        -WindowStyle Hidden | Out-Null

    Write-Host "Documenter launched for $targetRelative"
}

Write-Host "Development-log monitor started."
Write-Host "Repository: $RepoRoot"
Write-Host "Interval: $IntervalMinutes minutes"
Write-Host "Press Ctrl+C to stop."

$startTime = Get-Date
$startTree = New-WorkingTreeSnapshot

while ($true) {
    Start-Sleep -Seconds ($IntervalMinutes * 60)

    $endTime = Get-Date
    $endTree = New-WorkingTreeSnapshot

    if ($startTree -ne $endTree) {
        $artifacts = Get-IntervalArtifacts `
            -StartTree $startTree `
            -EndTree $endTree `
            -StartTime $startTime `
            -EndTime $endTime

        $diffLength = (Get-Item $artifacts.DiffFile).Length

        if ($diffLength -gt 0) {
            Start-Documenter `
                -StartTime $startTime `
                -EndTime $endTime `
                -DiffFile $artifacts.DiffFile `
                -MetaFile $artifacts.MetaFile
        }
    }
    else {
        Write-Host "No relevant changes in $($startTime.ToString("HH:mm"))–$($endTime.ToString("HH:mm"))."
    }

    # S1 becomes the next interval's S0.
    $startTime = $endTime
    $startTree = $endTree
}

Error que debes evitar: modificar código después del staging y ejecutar /review sin volver a preparar los cambios. Claude volvería a revisar el candidato anterior.
OpenCode 
/implement Fix the accepted findings from the previous review without expanding the task scope.
PowerShell 
git diff
git add -A
git diff --cached --stat
OpenCode 
/review
Después de cada corrección actualizo el staging antes de revisar.
Ese gesto es el que hace que git diff --cached represente la nueva versión.

Quitar todo del staging sin borrar el trabajo

PowerShell 
git restore --staged .

15. Commit final: siempre humano

PowerShell — antes del commit 
git status
git diff --cached --stat
git diff --cached
Entiendo todos los archivos staged y la revisión final es aceptable.
El criterio no es “Claude dijo OK”; el criterio es que tú aceptas el candidato y su validación.
PowerShell 
git commit -m "type: concise description"
PowerShell — después 
git status
git log -1 --oneline
El commit existe y el working tree queda como esperaba.
Push y merge siguen el flujo que marque el bootcamp.
