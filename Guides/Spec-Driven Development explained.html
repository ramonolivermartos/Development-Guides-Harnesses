Write down what you want to build before asking the AI to build it

Spec-Driven Development (SDD) is a way of developing in which the specification is the source of truth. You describe the expected behavior precisely; the plan, the tasks and the code come from it and are checked against it.

What problem it solves

With AI assistants it is very easy to ask for code and very hard to know whether it is the right code. Compare what happens with the same request.

The SDD cycle

Four phases. Each one produces a document that the next one takes as input, and you review it before moving on.

The golden rule: if the result is not what you wanted, fix the specification or the plan first and regenerate. Patching only the code makes the document and the program drift apart.

When to use it and with which tools

It is worth it if

  • The project has several features that touch each other.
  • You are going to work with other people or with several AI sessions.
  • The cost of getting it wrong is high (data, payments, security).
  • You want to be able to change technology without losing the what.

Better without it if

  • It is a throwaway script or a prototype for exploring.
  • The task fits in a small, clear change.
  • You do not know yet what you want: explore first and specify later.

Tools that apply it

GitHub Spec Kit: commands such as /specify, /plan, /tasks and /implement, and a /constitution to set the project's principles.
Kiro: an IDE that generates requirements.md, design.md and tasks.md for each feature.
OpenSpec and Tessl: other approaches that keep the specs inside the repository alongside the code.
Without a tool: three markdown files (spec, plan, tasks) and your favorite assistant are already SDD.
SDD is a young approach: the names of commands and tools change quickly, but the cycle of specifying, planning, breaking down and implementing stays the same.
