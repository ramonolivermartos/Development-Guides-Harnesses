Guía interactiva: Git + GitHub sin GitHub Actions

Guía organizada en tres capas: flujo normal de trabajo, operaciones útiles de Git y banco de errores/recuperación.

✓ Tú controlas Git
Los comandos se ejecutan conscientemente; no automatizamos commits ni merges.
✓ Rama principal: main
La guía usa main como rama principal.
✓ Flujo con ramas
El trabajo normal no se desarrolla directamente sobre main.
✓ GitHub como remoto
Los Pull Requests y reviews viven en GitHub; los commits y ramas pertenecen a Git.
Objetivo final: interiorizar un ciclo estable: sincronizar main → crear rama → trabajar → inspeccionar → stage → commit → push → Pull Request → review → merge → actualizar main → eliminar rama.
Regla de seguridad: esta guía evita recomendar git reset --hard, git clean -fd y force push como operaciones normales. Son herramientas válidas, pero destructivas si todavía no entiendes exactamente qué van a borrar o reescribir.

0. Modelo mental: qué mueve realmente Git

Antes de memorizar comandos, memoriza los estados. Git no es “guardar en GitHub”. Git trabaja primero en tu máquina.

Working tree→ git add → Staging area→ git commit → Repositorio local→ git push → GitHub / origin
Working treeLos archivos tal como existen ahora mismo en tu carpeta.
Staging area / indexLa selección exacta de cambios que entrará en el próximo commit.
CommitUna fotografía identificada del estado seleccionado. Vive en tu repositorio local.
RemoteOtra copia del repositorio. En esta guía el remoto principal se llama origin y vive en GitHub.
Idea crítica: git add no “sube” nada a GitHub. git commit tampoco. Solo git push envía commits al remoto.
main actualizado→ feature/... → cambios→ stage→ commit→ push→ PR→ merge
Distingo Git de GitHub.Git gestiona historial, ramas, commits y merges. GitHub aloja el remoto y añade Pull Requests, review e interfaz colaborativa.
Un repositorio Git funciona perfectamente sin GitHub.
Entiendo los tres estados locales.Working tree → staging → commit.
Si esta cadena está clara, la mayoría de comandos dejan de parecer arbitrarios.

PowerShell

PowerShell

4.4 Crear el commit

PowerShell

4.5 Comprobar

PowerShell

5. Crear el repositorio remoto en GitHub

  1. En GitHub, crea un repositorio nuevo.
  2. Usa el nombre que quieras para el proyecto.
  3. Elige público o privado según corresponda.
  4. No añadas README, .gitignore ni licencia desde GitHub si ya tienes un repositorio local con su primer commit.
  5. Crea el repositorio vacío y copia su URL HTTPS o SSH.
Por qué lo dejamos vacío: si GitHub crea su propio commit inicial y tu repositorio local ya tiene otro historial independiente, tendrás dos raíces distintas y complicas innecesariamente la primera sincronización.
HTTPS
Más simple para empezar. Ejemplo: https://github.com/USUARIO/REPO.git.
SSH
Muy cómodo cuando ya tienes tus claves configuradas. Ejemplo: git@github.com:USUARIO/REPO.git.
He creado un repositorio remoto vacío.
Sin README remoto ni otro commit inicial.
Tengo copiada la URL correcta del repositorio.
HTTPS y SSH son válidos; no mezcles URLs de otro proyecto.

9. Preparar el candidato a commit: staging

Añadir un archivo concreto

PowerShell

Añadir varios archivos concretos

PowerShell

Seleccionar fragmentos interactivos

PowerShell

Añadir todo lo actual

PowerShell

Revisar el candidato exacto

PowerShell

git diff --cached
Distinción que debes interiorizar: git diff muestra cambios no staged. git diff --cached muestra lo que entrará en el próximo commit.

Sacar un archivo del staging sin borrar su modificación

PowerShell 
git restore --staged ruta/al/archivo.java
El staging contiene una unidad lógica de trabajo.
Un commit no debería mezclar una feature, un refactor ajeno y cambios de formato accidentales.
He revisado git diff --cached.
Éste es tu candidato real al commit.

11. Publicar tu rama en GitHub

La primera vez que subes una rama local nueva, crea su upstream remoto.

PowerShell

Después, mientras sigas en esa misma rama:

PowerShell

Comprobar tracking

PowerShell 
git branch -vv
git status
Push no crea un Pull Request. Solo publica commits y actualiza la rama remota. El PR es una operación aparte en GitHub.
La rama está publicada en origin.
Debe aparecer en GitHub.
La rama local tiene upstream.
Así los siguientes git push son simples.

  • Confirma que no hay archivos accidentales.
  • Comprueba que el PR tiene un objetivo único.
  • Escribe un título que describa el resultado.
  • Explica qué cambia y cómo se validó.

Plantilla mental mínima

Descripción del Pull Request

- ...

- ...

- ...

## Notas
- ...
No uses el Pull Request como papelera de todo lo hecho durante varios días. Si la comparación es enorme y mezcla objetivos, el problema empezó antes: la rama o los commits tienen demasiado alcance.
Base y compare son correctas.
Normalmente main ← feature/....
He revisado “Files changed”.

El PR explica cambio, motivo y validación.

13. Review: corregir sin abrir otro Pull Request

Si el review detecta algo, continúas trabajando en la misma rama. El Pull Request se actualiza automáticamente cuando haces nuevos pushes a esa rama.

review→ corregir local→ git add→ git commit→ git push→ mismo PR actualizado
PowerShell — ciclo de corrección 
git status
git diff
# corrige los archivos
git add ruta/al/archivo
git diff --cached
git commit -m "fix: address review feedback"
git push
No necesitas cerrar y recrear el PR. Un PR compara ramas, no “un commit concreto”. Mientras empujes a la misma rama de origen, GitHub recalcula la comparación.
Las correcciones se han hecho en la misma rama del PR.
El PR debe actualizarse automáticamente.
He vuelto a revisar el diff y la validación.
Una corrección también puede introducir regresiones.

14. Integrar el Pull Request: merge

Cuando el PR esté aprobado y listo, GitHub suele ofrecer varias estrategias. Para proyectos personales o educativos, conviene entenderlas en vez de pulsar la primera opción.

EstrategiaQué haceCuándo tiene sentido
Create a merge commitConserva los commits de la rama y crea un commit de merge.Quieres preservar explícitamente la topología de ramas.
Squash and mergeCombina todo el PR en un único commit sobre main.Muy práctico cuando los commits intermedios son ruidosos y el PR representa una sola unidad lógica.
Rebase and mergeReaplica los commits de la rama linealmente sobre main.Quieres historial lineal conservando commits individuales.
Para empezar: si cada Pull Request representa una tarea bien delimitada, Squash and merge suele producir un historial sencillo de leer. Pero no es una ley universal; sigue la convención del proyecto cuando exista.
El PR está revisado y validado antes de mergear.
Merge no sustituye review ni tests.
Entiendo qué estrategia de merge estoy usando.
No elijas por inercia.
El Pull Request aparece como merged.
Ahora el cambio existe en origin/main.

16. Cerrar el ciclo: eliminar la rama ya integrada

Eliminar la rama local

PowerShell 
git branch -d feature/nombre-corto

La opción -d es deliberadamente conservadora: Git se niega si considera que la rama contiene trabajo no integrado.

Eliminar la rama remota

Si GitHub no la eliminó automáticamente al mergear:

PowerShell 
git push origin --delete feature/nombre-corto

Limpiar referencias remotas obsoletas

PowerShell 
git fetch --prune
No uses git branch -D por costumbre. La mayúscula fuerza el borrado aunque Git detecte trabajo no integrado. Úsala solo cuando sepas por qué la rama se puede descartar.
La rama mergeada ya no existe localmente.
Evita acumular ramas muertas.
Las referencias remotas están limpias.
git fetch --prune elimina referencias a ramas remotas que ya no existen.

Cosas que podemos hacer con Git

Operaciones útiles que amplían tu caja de herramientas. No tienes que ejecutarlas en cada tarea: las usas cuando la situación lo requiere.

18. Entender fetch, pull y push

ComandoDirecciónQué hace
git fetchGitHub → datos locales de seguimientoDescarga información del remoto sin integrar esos cambios en tu rama actual.
git pullGitHub → rama localObtiene cambios remotos e intenta integrarlos en la rama actual.
git pushRepositorio local → GitHubPublica commits locales que el remoto todavía no tiene.

Inspeccionar antes de integrar

PowerShell 
git fetch origin
git status
git log --oneline --graph --decorate --all -15
Modelo corto: fetch informa, pull informa e integra, push publica.
Sé cuándo prefiero fetch a pull.
Si quieres inspeccionar primero, usa fetch.

19. Apartar trabajo temporalmente con git stash

Úsalo cuando necesitas dejar temporalmente el working tree limpio sin crear un commit artificial.

Guardar cambios tracked

PowerShell 
git stash push -m "WIP: user registration"

Incluir también archivos untracked

PowerShell 
git stash push -u -m "WIP: user registration"

Ver stashes

PowerShell 
git stash list

Recuperar sin borrar la entrada

PowerShell 
git stash apply stash@{0}

Recuperar y eliminar la entrada si funciona

PowerShell 
git stash pop
Stash no es un archivo permanente. No lo conviertas en un cementerio de trabajo olvidado. Si algo merece conservarse y explicarse, probablemente merece una rama y commits.
Uso stash solo como almacenamiento temporal.
Pon mensajes descriptivos si vas a tener más de uno.

20. “Lo he añadido al .gitignore y Git sigue viéndolo”

.gitignore afecta a archivos que Git todavía no rastrea. Si un archivo ya está trackeado, ignorarlo no lo saca del repositorio.

Dejar de trackear un archivo sin borrarlo del disco

PowerShell 
git rm --cached ruta/al/archivo

Para una carpeta

PowerShell 
git rm -r --cached ruta/a/la/carpeta

Después, confirma que la ruta está correctamente ignorada y crea un commit.

Si el archivo contenía un secreto y ya fue commiteado, quitarlo del estado actual no elimina el secreto del historial anterior. En ese caso debes considerar el secreto comprometido, rotarlo y limpiar el historial con un procedimiento específico.
Entiendo que “ignored” y “untracked” no significan lo mismo que “dejar de trackear”.
Git no olvida automáticamente un archivo que ya forma parte de su historial.

21. Empezar desde un repositorio que ya existe: git clone

Si el proyecto ya existe en GitHub, normalmente no haces git init + remote add. Lo clonas.

PowerShell 
git clone https://github.com/USUARIO/REPOSITORIO.git
cd REPOSITORIO
Comprobar 
git status
git remote -v
git branch -vv
Clone ya hace varias cosas: crea la carpeta, copia el historial Git, configura origin y prepara la rama inicial de trabajo.
Sé distinguir “proyecto local nuevo” de “repositorio remoto existente”.
Nuevo local: git init. Existente remoto: git clone.

Banco de errores y recuperación

Cuando Git se desvía del flujo normal, vienes aquí. Primero diagnostica; después aplica la corrección menos destructiva que resuelva el estado real.

23. Resolver conflictos de merge sin pánico

Un conflicto no significa que Git esté roto. Significa que Git no puede decidir automáticamente cómo combinar dos modificaciones incompatibles.

Detectar conflicto 
git status

Marcadores típicos dentro del archivo

Ejemplo 
<<<<<<< HEAD
versión de tu rama actual
=======
versión que se intenta integrar
>>>>>>> otra-rama

Procedimiento

  1. Abre cada archivo marcado como conflictivo.
  2. Decide cuál debe ser el contenido final.
  3. Elimina los marcadores <<<<<<<, ======= y >>>>>>>.
  4. Guarda el archivo.
  5. Márcalo como resuelto con git add.
  6. Comprueba de nuevo git status.
  7. Completa la operación cuando todos los conflictos estén resueltos.
Después de resolver 
git add ruta/al/archivo-conflictivo
git status
No elijas “ours” o “theirs” sin leer el código. Resolver un conflicto es una decisión semántica, no una operación de limpieza de texto.
He entendido qué cambios compiten.
No borres una versión solo para hacer desaparecer los marcadores.
He validado el resultado después de resolverlo.
Un conflicto puede resolverse sintácticamente y dejar comportamiento incorrecto.

24. Deshacer cambios: elegir la operación correcta

Quiero descartar cambios no staged de un archivo
git restore archivo
Quiero sacar algo del staging pero conservar el archivo modificado
git restore --staged archivo
Quiero corregir el último commit local antes de publicarlo
git commit --amend
Quiero deshacer un commit que ya es historia compartida
git revert <commit>

Descartar modificaciones locales de un archivo

Destructivo para ese archivo 
git restore ruta/al/archivo

Des-stagear sin perder el cambio

Seguro para el contenido del working tree 
git restore --staged ruta/al/archivo

Modificar el último commit todavía no compartido

Reescribe el último commit 
git add ruta/al/archivo
git commit --amend

Revertir un commit compartido

Crea un nuevo commit inverso 
git revert HASH_DEL_COMMIT
Regla práctica: si un commit ya se ha publicado y otras personas pueden depender de él, evita reescribir su historia. git revert suele ser más seguro porque añade historia en vez de cambiar la existente.
git restore archivo sí puede destruir trabajo no guardado. Úsalo solo cuando realmente quieres descartar esas modificaciones.
Distingo des-stagear de descartar.
restore --staged conserva cambios; restore archivo los descarta.
Distingo reescribir historia de crear una reversión.
Es esencial cuando el trabajo ya se ha compartido.

25. Diagnóstico rápido: “¿dónde estoy y qué está pasando?”

Cuando algo no cuadra, no empieces a lanzar comandos de reparación al azar. Primero recopila estado.

Bloque de diagnóstico seguro 
git rev-parse --show-toplevel
git status
git branch --show-current
git branch -vv
git remote -v
git log --oneline --decorate --graph --all -15
PreguntaComando principal
¿Estoy dentro del repositorio correcto?git rev-parse --show-toplevel
¿Qué archivos han cambiado?git status
¿Qué he cambiado pero aún no está staged?git diff
¿Qué entrará en el próximo commit?git diff --cached

Banco de errores frecuentes

Mensaje o síntomaCausa probableRespuesta segura
fatal: not a git repositoryEstás fuera de la carpeta del repositorio o en una carpeta que no contiene .git.Localiza la raíz con tu explorador/terminal, entra en ella y comprueba con git rev-parse --show-toplevel.
remote origin already existsYa existe un remoto llamado origin.Ejecuta git remote -v. Si la URL es incorrecta, usa git remote set-url origin URL_CORRECTA; no añadas un segundo origin.
rejected / non-fast-forwardEl remoto contiene commits que tu rama local todavía no integra.Haz git fetch origin, inspecciona el historial y después integra de forma consciente. No respondas con --force por reflejo.
has no upstream branchLa rama local todavía no está asociada a una rama remota.En el primer push usa git push -u origin NOMBRE_RAMA.
nothing to commit, working tree cleanNo hay cambios pendientes para commitear.No es un error. Si esperabas cambios, comprueba que guardaste los archivos y que estás en el repositorio correcto.
changes not staged for commitHay cambios en el working tree, pero no están en staging.Inspecciona con git diff y añade solo lo que quieras incluir con git add.
local changes would be overwrittenIntentas cambiar/integrar mientras tienes modificaciones locales incompatibles.Decide conscientemente entre commit, stash o descartar. No borres cambios para desbloquear Git sin saber si los necesitas.
CONFLICT / unmerged pathsGit no puede combinar automáticamente cambios incompatibles.Ve a la sección Resolver conflictos, resuelve el contenido y valida antes de continuar.
Un archivo sigue apareciendo aunque está en .gitignoreEl archivo ya estaba trackeado antes de añadir la regla de ignore.Ve a Archivos ya trackeados. El .gitignore no hace que Git olvide archivos ya versionados.
He staged algo que no queríaEl staging contiene más cambios de los deseados.Usa git restore --staged archivo. Conserva el contenido modificado en tu working tree.
He commiteado algo incorrectoEl commit ya existe; la respuesta depende de si se publicó o no.Ve a Deshacer cambios: --amend para el último commit local no compartido; revert cuando ya forma parte de historia compartida.
No uses “comandos de Internet” para arreglar Git sin saber qué estado tienes. Especialmente evita copiar a ciegas comandos con --hard, --force o clean.
Antes de reparar, sé diagnosticar el estado.
Git suele ser mucho más fácil de arreglar cuando todavía no has ejecutado una operación destructiva.

Mapa conceptual final

archivo modificado→ add → staged→ commit → commit local→ push → rama GitHub→ PR → review→ merge → origin/main→ pull → main local actualizado
