BLOQUE A · QUÉ VAMOS A CONSTRUIR

De la idea a los requisitos

Primero comprender el problema. Todavía no hay tablas, controladores ni paquetes Java.

PASO 00

Modelo mental: qué es preparar un proyecto

Comprende qué vamos a producir y qué NO corresponde a esta guía.

0 / 0

El objetivo es pasar de una idea vaga a un conjunto de decisiones y documentos que permitan empezar a construir una aplicación sin improvisar la arquitectura en cada archivo.

Problema→MVP→Casos de uso→Modelo de dominio→Diseño técnico→Spring Boot→git init
No confundas tres niveles: “un usuario puede registrar un libro” es un requisito; “POST /api/books” es un contrato API; “BookController” es una decisión de implementación. No diseñes todo al mismo tiempo.
ConceptoQué significaEjemplo
ProblemaNecesidad real que justifica el software.No recuerdo qué libros tengo pendientes.
DominioConceptos y reglas del problema.Libro, biblioteca, estado de lectura.
MVPVersión mínima útil con alcance controlado.Añadir y consultar mis libros.
ContratoComportamiento externo prometido.GET /api/books devuelve una lista.
ImplementaciónCódigo que cumple el contrato.Controller, Service, Repository.
PASO 01

Preparar la carpeta y el vault de Obsidian

Elige dónde vivirán los archivos y cómo vas a abrirlos.

0 / 0

Vault significa “carpeta de notas que Obsidian abre”. No es una base de datos especial: son archivos normales, sobre todo Markdown (.md).

Para no duplicar documentación, una opción limpia es que la carpeta raíz del proyecto sea también el vault. Las notas técnicas se guardarán en docs/ y el código, cuando exista, en src/.

PowerShell — ejemplo de ruta, personalízala
$project = "C:\Dev\Projects\BookTrack"
New-Item -ItemType Directory -Force $project | Out-Null
Set-Location $project
Get-Location

En Obsidian: abre el selector de vaults (o menú del vault actual), elige Open folder as vault / Abrir carpeta como vault, señala C:\Dev\Projects\BookTrack y confirma. No abras la carpeta padre Projects.

Obsidian creará una carpeta .obsidian/ con ajustes y plugins. Cuando llegues a la guía de Git, decide si versionas esa configuración; para un proyecto personal suele ser mejor añadir .obsidian/ al .gitignore. Tu plantilla actual de .gitignore no incluye esta regla.
PASO 02

Instalar y usar Excalidraw en Obsidian

Un lienzo libre para pensar, no para formalizar arquitectura.

0 / 0

Excalidraw es una pizarra donde puedes dibujar cajas, conexiones y texto sin decidir todavía qué será una clase o una tabla.

  1. Abre Settings / Ajustes en Obsidian.
  2. Entra en Community plugins / Plugins de la comunidad.
  3. Activa el uso de plugins comunitarios si se solicita; son código de terceros.
  4. Pulsa Browse, busca Excalidraw, revisa que es el plugin previsto y pulsa Install y Enable.
  5. Abre la paleta con Ctrl + P, busca Excalidraw y ejecuta su opción para crear un dibujo nuevo.
  6. Guarda el dibujo en docs/00-brainstorming/ y renómbralo a algo reconocible.
Si no encuentras el comando: comprueba que el plugin esté habilitado en el vault actual. Cada vault puede tener su propia configuración.
PASO 03

Brainstorming sin filtrar ideas

Genera posibilidades antes de seleccionar el MVP.

0 / 0

En el centro del lienzo escribe la idea en una frase. Alrededor añade notas con problema, usuarios, acciones, dudas, restricciones e ideas futuras. En esta etapa una idea no se convierte automáticamente en requisito.

Ejemplo de preguntas iniciales — cópialas al lienzo
PROBLEM: What specific problem am I trying to solve?
USERS: Who will actually use the application?
ACTIONS: What can each user do?
DATA: What information must the system store?
RULES: What is allowed and what is forbidden?
OPEN QUESTIONS: What do I need to research or decide?
FUTURE IDEAS: What could I add later?
CONSTRAINTS: time, resources, budget, privacy
Criterio de salida: no hace falta un dibujo bonito. Sí hace falta entender quién usa el sistema, para qué y qué acciones imaginas.

PASO 05

Definir alcance y MVP

Decide qué entra, qué queda fuera y qué se pospone.

0 / 0

MVP significa Minimum Viable Product: la versión mínima que ofrece utilidad o permite validar la idea. No significa “versión hecha deprisa” ni “todo el producto con menos calidad”.

Plantilla — docs/01-project/Scope-MVP.md
# Scope and MVP

## First Release Goal
Allow readers to manage the books in their personal library.

## In Scope for the MVP
- Add a book.
- List books.
- Update a book's reading status.
- Remove a book from the library.

## Out of Scope for the MVP
- AI-powered recommendations.
- Social networking features.
- Bulk catalog imports.

## Constraints
- The backend will be built with Spring Boot.
- No mobile application will be included in the first release.

## MVP Completion Criteria
All four actions can be executed with defined success responses and error handling.
¿Dónde va?Prueba rápida
MVPSin esto, la primera versión no cumple su propósito.
PosteriorAporta valor, pero el MVP funciona sin ello.
DescartadoNo resuelve el problema o contradice una restricción.
PASO 06

Identificar actores y reglas de negocio

Entiende quién actúa y qué condiciones impone el dominio.

0 / 0

Un actor es alguien o algo externo que interactúa con el sistema (p. ej., usuario o servicio externo). Una regla de negocio define qué comportamientos son válidos independientemente de la tecnología.

Plantilla — docs/02-domain/Actors-and-Rules.md
# Actors and Business Rules

## Actors
- Reader: views and modifies their personal library.
- Administrator: out of scope for the MVP.

## Business Rules
- The same book cannot be added twice to a reader's library.
- A reading status must be one of the permitted values.
- A book title must not be empty.

## Open Questions
- Is a Book shared globally or owned by an individual library?
No inventes reglas por estética. Si la regla no procede de un requisito o de una necesidad clara del dominio, márcala como hipótesis.
PASO 07

Crear el glosario del dominio

Define palabras antes de repetirlas en código y diagramas.

0 / 0

El dominio es el conjunto de conceptos del problema. Un glosario evita que ReadingStatus, BookState y Status acaben significando cosas distintas o redundantes.

Plantilla — docs/02-domain/Glossary.md
# Domain Glossary

## Book
A published work that can be added to a library.

## Library
A collection of books registered by a reader.

## LibraryEntry
An association between a reader and a book, including its reading status.

## ReadingStatus
- WISHLIST
- READING
- FINISHED
- ABANDONED

## Terms That Are Not Synonyms
Book != LibraryEntry: the same book can appear in multiple libraries.
PASO 08

Convertir el MVP en casos de uso

Cada objetivo del usuario debe ser describible y comprobable.

0 / 0

Un caso de uso describe una interacción orientada a un resultado. No es un endpoint ni un método Java. Primero define qué hace el usuario; la API vendrá después.

Ejemplo — docs/03-use-cases/UC-01-Add-Book.md
# UC-01 — Add a Book to the Library

## Actor
Reader.

## Goal
Save a book in the reader's personal library.

## Preconditions
The reader has a library.

## Main Flow
1. The reader submits the book information.
2. The system validates the required fields.
3. The system adds an entry to the library.
4. The system confirms the result.

## Alternative Flows / Errors
- Required information is missing: the operation is rejected.
- The book already exists in this library: the system reports a conflict.

## Acceptance Criteria
- A valid entry is persisted.
- A duplicate entry is not created.
- The response identifies the newly created entry.
Un formato simple basta: actor → precondición → pasos → errores → criterio de aceptación. Los casos de uso complicados pueden tener diagramas después.

PASO 09

Diseñar la arquitectura a alto nivel

Comprende qué piezas existirán y qué responsabilidad tienen.

0 / 0

La arquitectura organiza responsabilidades y dependencias. En un backend REST sencillo puedes partir de capas, pero debes adaptarlas al problema, no crear archivos vacíos por rutina.

Cliente HTTP→Controller→Service→Repository→Base de datos
PiezaResponsabilidadNo debería hacer
ControllerRecibir peticiones, validar entrada y devolver respuestas HTTP.Implementar todas las reglas de negocio.
ServiceEjecutar casos de uso y reglas.Construir respuestas HTTP manualmente.
RepositoryConsultar y guardar datos persistidos.Decidir permisos del usuario.
EntityRepresentar datos de persistencia.Ser automáticamente el JSON público de la API.
DTORepresentar solicitudes y respuestas de la API.Consultar directamente la base de datos.
Plantilla — docs/04-architecture/Overview.md
# Initial Architecture

## Architectural Style
HTTP REST backend built with Spring Boot, with clear separation of responsibilities.

## Typical Request Flow
HTTP Client -> Controller -> Service -> Repository -> Database

## Open Decisions
- Package structure: feature-based or layer-based.
- Whether authentication is required in the MVP.
- Persistence technology.

## Architectural Rules
- Controllers do not contain business rules.
- DTOs define the external API contract.
- The persistence model does not automatically define the HTTP contract.
PASO 10

Organizar los conceptos con Obsidian Canvas

Pasa del dibujo libre a un mapa navegable de notas.

0 / 0

Canvas y Excalidraw no son lo mismo. Excalidraw es pizarra libre; Canvas organiza tarjetas y enlaces a notas reales. Puedes prescindir de Canvas si todavía no aporta valor.

  1. En Obsidian busca Canvas (complemento principal) y actívalo si está desactivado.
  2. Crea un Canvas nuevo en docs/02-domain/.
  3. Arrastra notas del glosario y casos de uso al lienzo.
  4. Conecta conceptos: LibraryEntry vincula Book y Library.
  5. No copies todo el texto de las notas al Canvas: deja enlaces.
Objetivo: poder navegar desde un concepto a su definición y a los casos de uso relacionados, sin duplicar su contenido.
PASO 11

UML de componentes en diagrams.net

Visualiza módulos y dependencias, sin detallar clases todavía.

0 / 0

UML significa Unified Modeling Language. Es un lenguaje para representar visualmente aspectos de un sistema; no se limita al diagrama de clases. El diagrama de componentes responde “¿qué piezas existen y cómo se comunican?”.

  1. Abre app.diagrams.net.
  2. Elige guardar en Device / Dispositivo para conservar el archivo local.
  3. Crea un diagrama en blanco.
  4. Inserta cuadros para API REST, Services, Persistence y Database.
  5. Une los cuadros mediante flechas que representen dependencias.
  6. Guárdalo como docs/09-diagrams/Architecture.drawio.
Una flecha no debería significar cosas distintas en el mismo dibujo. Define una pequeña leyenda: “A → B” significa “A depende de B / llama a B”.

Modela entidades conceptuales, atributos importantes y relaciones.

0 / 0

Un diagrama de clases describe tipos y sus relaciones. En esta fase prioriza las clases de dominio, no BookController ni cada servicio futuro.

UML no es el ER: UML habla de conceptos/clases y relaciones del dominio; ER habla de tablas, claves y restricciones de almacenamiento. Se parecen, pero no son intercambiables.
PASO 13

Modelo ER con dbdiagram.io y DBML

Convierte relaciones del dominio en un borrador de almacenamiento.

0 / 0

ER = Entidad–Relación. Describe tablas, columnas, claves primarias (PK), claves foráneas (FK) y cardinalidades. Una FK apunta a la PK u otra clave identificadora de otra tabla.

DBML es un lenguaje textual para describir bases de datos de manera legible; dbdiagram.io dibuja el esquema a partir de él.

Ejemplo — docs/05-database/schema.dbml
Table users {
  id bigint [pk, increment]
  email varchar [not null, unique]
}

Table books {
  id bigint [pk, increment]
  title varchar [not null]
}

Table library_entries {
  id bigint [pk, increment]
  user_id bigint [not null]
  book_id bigint [not null]
  status varchar [not null]

  indexes {
    (user_id, book_id) [unique]
  }
}

Ref: library_entries.user_id > users.id
Ref: library_entries.book_id > books.id
  1. Abre dbdiagram.io.
  2. Crea un diagrama nuevo.
  3. Pega el DBML de ejemplo o escribe el de tu proyecto.
  4. Observa cómo se crean las tablas y las líneas.
  5. Corrige relaciones y restricciones.
  6. Guarda el texto DBML en el proyecto, incluso si también lo conservas en tu cuenta de dbdiagram.
No confundas modelo con base de datos creada: este archivo todavía no ejecuta SQL en PostgreSQL ni crea tablas reales. Es una especificación de diseño.
PASO 14

Comprobar el salto de UML a ER

Evita que el almacenamiento contradiga el dominio.

0 / 0

Una clase del dominio no tiene por qué ser exactamente una tabla. Algunas clases son valores o comportamientos; otras se representan mediante tablas de unión. Lo relevante es que el diseño permita cumplir las reglas del negocio.

Dominio / reglaImpacto posible en ER
Una biblioteca contiene muchas entradas.Tabla library_entries vinculada a usuario/biblioteca.
No debe haber dos entradas iguales para un usuario y libro.Índice único compuesto.
Cada entrada tiene un estado válido.Columna status + validación; evaluar CHECK/enum.
Una obra aparece en varias bibliotecas.Entidad books separada de la entrada.
No elijas todavía FetchType.EAGER, cascadas JPA o mappers concretos si no tienes contexto. Eso es diseño de persistencia más detallado y se validará al implementar.
PASO 15

Diseñar endpoints a partir de casos de uso

Traduce acciones funcionales a recursos HTTP.

0 / 0

Un endpoint es la combinación de una ruta, un método HTTP y un comportamiento. GET lee; POST crea o inicia operaciones; PATCH modifica parcialmente; DELETE elimina.

Caso de usoMétodo y rutaResultado esperado
UC-01 Añadir libroPOST /api/books201 Created y cuerpo.
UC-02 Consultar librosGET /api/books200 OK y lista.
UC-03 Consultar unoGET /api/books/{id}200 o 404.
UC-04 Cambiar estadoPATCH /api/books/{id}200/204 o error.
UC-05 Eliminar entradaDELETE /api/books/{id}204 No Content.

Las rutas de la tabla son ejemplo. Decide si /books significa catálogo global o biblioteca del usuario; esa decisión afecta la API. No copies el ejemplo sin definir qué recurso representa cada ruta.

Plantilla — docs/06-api/Endpoint-Matrix.md
# Endpoint Matrix

| Use Case | Method | Path | Request | Response | Errors |
| --- | --- | --- | --- | --- | --- |
| UC-01 | POST | /api/library-entries | CreateEntryRequest | EntryResponse | 400, 409 |
| UC-02 | GET | /api/library-entries | Query filters | EntryResponse[] | 400 |

## Open Questions
- Is authentication required?
- Who may view or modify each resource?
- Is pagination included in the MVP?
Si el diseño exige autenticación, debes especificar quién puede hacer cada operación. No lo dejes implícito y luego lo soluciones con permitAll() para que “funcione”.
PASO 16

OpenAPI antes del código: diseñar el contrato

Escribe un contrato válido que después Spring Boot deberá cumplir.

0 / 0

OpenAPI es un documento estándar (por ejemplo openapi.yaml) que define rutas, métodos, entradas, salidas y errores. Swagger Editor ayuda a redactarlo y validarlo; Swagger UI lo presenta de forma interactiva. Ninguno sustituye automáticamente el backend.

Ejemplo completo y válido — api/openapi.yaml
openapi: 3.0.3
info:
  title: BookTrack API
  version: 0.1.0
  description: Initial API contract for the BookTrack MVP.
servers:
  - url: http://localhost:8080
paths:
  /api/library-entries:
    get:
      summary: List library entries
      operationId: listLibraryEntries
      responses:
        '200':
          description: Library entries retrieved successfully
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: '#/components/schemas/EntryResponse'
    post:
      summary: Add an entry to the library
      operationId: createLibraryEntry
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: '#/components/schemas/CreateEntryRequest'
      responses:
        '201':
          description: Library entry created successfully
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/EntryResponse'
        '400':
          description: Invalid request data
        '409':
          description: Duplicate library entry
components:
  schemas:
    CreateEntryRequest:
      type: object
      required: [bookId, status]
      properties:
        bookId:
          type: integer
          format: int64
          example: 7
        status:
          type: string
          enum: [WISHLIST, READING, FINISHED, ABANDONED]
    EntryResponse:
      type: object
      required: [id, bookId, status]
      properties:
        id:
          type: integer
          format: int64
        bookId:
          type: integer
          format: int64
        status:
          type: string
          enum: [WISHLIST, READING, FINISHED, ABANDONED]
  1. Crea la carpeta api/ si todavía no existe.
  2. Crea y guarda api/openapi.yaml con un editor de texto o código.
  3. Abre Swagger Editor y pega el contenido.
  4. Comprueba que se rendericen las operaciones sin errores de sintaxis.
  5. Adapta rutas, esquemas y errores a tus casos de uso reales.
  6. Vuelve a guardar el YAML final en api/openapi.yaml.
Matiz importante: que Swagger Editor valide el YAML no prueba que el diseño sea bueno ni que exista un backend funcional. Solo comprueba la especificación; el contrato será contrastado con el código cuando implementes la API.
PASO 17

Comprobar contratos, errores y seguridad

Evita ambigüedades que luego se trasladan al código.

0 / 0

Para cada operación define: datos obligatorios, formato, éxito, error y permisos. Un 404 no equivale a un 400: el primero suele indicar que el recurso no existe; el segundo que la solicitud es inválida.

Estado HTTPSignificado frecuenteEjemplo
200Petición correcta con respuesta.Listado de entradas.
201Recurso creado.Nueva entrada.
204Correcto sin cuerpo.Eliminación.
400Solicitud inválida.Estado de lectura desconocido.
401Falta autenticación válida.Token ausente o inválido.
403Acceso denegado.No eres propietario.
404Recurso no encontrado.ID inexistente.
409Conflicto de estado.Duplicado.
No elijas JWT, sesiones o proveedores de identidad por moda. Primero define si el MVP necesita cuentas y autorización, después decide el mecanismo que lo resuelve.

PASO 18

Elegir stack tecnológico con criterio

Selecciona dependencias por requisitos, no por acumulación.

0 / 0

Stack significa conjunto de herramientas y tecnologías. Dependencia es una biblioteca o componente que el proyecto necesita para compilar o funcionar. Spring Initializr ofrece “starters” que agrupan dependencias compatibles.

Tecnología¿Para qué sirve?¿Cuándo añadirla?
Java + Spring BootLenguaje y plataforma del backend.Base del proyecto.
MavenConstruir, probar y gestionar librerías mediante pom.xml.Elige Maven o Gradle, no ambos.
Spring WebExponer endpoints HTTP.Si el MVP ofrece REST.
ValidationValidar DTOs y entradas.Si hay formularios o cuerpos JSON.
Spring Data JPAPersistencia relacional con entidades.Si habrá base de datos SQL y JPA.
PostgreSQL DriverConectar con PostgreSQL.Solo si ese es el motor elegido.
Spring SecurityAutenticación y autorización.Solo si hay requisitos de seguridad que lo justifiquen.
Testing starterTests.Desde el inicio, usando lo incluido en la versión elegida.

# Technology Stack

## Platform
- Java: an LTS version compatible with the selected Spring Boot version.
- Spring Boot: a stable version selected in Spring Initializr.
- Build tool: Maven Wrapper.

PASO 25

Generar Spring Boot con Spring Initializr

Crea el esqueleto de aplicación sin inventar estructura a mano.

0 / 0

Spring Initializr es un generador oficial del esqueleto de un proyecto. Produce un ZIP con la estructura inicial, el archivo de build y el wrapper. No crea por sí solo toda la lógica del MVP.

  1. Abre start.spring.io.
  2. En Project, elige Maven (nuestro ejemplo).
  3. En Language, selecciona Java.
  4. En Spring Boot, elige una versión estable compatible con tu JDK (evita snapshots y milestones salvo motivo concreto).
  5. En Group, escribe tu namespace, por ejemplo dev.example. En Artifact, un identificador breve como booktrack.
  6. Revisa Name, Description, Package name y Packaging = Jar.
  7. Selecciona la versión de Java compatible con tu entorno.
  8. En Add Dependencies, empieza por las dependencias del stack que sí has justificado (por ejemplo Spring Web y Validation). No añadas JPA, Security o un driver sin decidir su configuración.
  9. Pulsa Generate; se descargará un ZIP. No lo extraigas todavía encima de archivos existentes sin revisarlo.
Ejemplo de metadatos que debes anotar
Project: Maven
Language: Java
Group: dev.example
Artifact: booktrack
Name: booktrack
Packaging: Jar
Java: selected compatible version
Spring Boot: selected stable compatible version
Dependencies: Spring Web, Validation (example)
group suele ser un identificador inverso de dominio u organización; artifact es el nombre técnico del módulo y del artefacto generado; package es la ubicación lógica base de clases Java. No son la misma cosa.
